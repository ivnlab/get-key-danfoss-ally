# get_local_key - инструмент извлечения Tuya local_key

*[English version](README.md)*

> **Дисклеймер:** инструмент предоставляется **как есть**, без каких-либо
> гарантий. Это грязный хак, построенный на сканировании памяти живого
> процесса Android-приложения - он стабильно работает в среде, где был
> разработан и протестирован (Windows + эмулятор LDPlayer), но точная
> причина нестабильности, описанной в разделе
> [«Известная нестабильность»](#известная-нестабильность-attach-иногда-убивает-приложение)
> ниже, так и не была установлена до конца, и в других средах (реальные
> телефоны, другие эмуляторы, другие версии ОС/frida) поведение может
> отличаться или инструмент может не заработать вовсе. Если не заработало
> у вас - откройте issue на GitHub и опишите свою среду (ОС, модель
> телефона/эмулятора, версия Android, версия `frida`/`frida-server`) и
> что именно вы делали и что получили - только так это можно сделать
> надёжнее со временем.

Извлекает `local_key` шлюза Danfoss Ally (и таблицу `nodeId`/`cid` его
Zigbee-суб-устройств) прямо из памяти процесса Android-приложения Danfoss
Ally, не требуя заранее знать ни один device_id.

Автоматизирует ручную процедуру, описанную в
[`docs/LOCAL_KEY_EXTRACTION_METHOD.md`](docs/LOCAL_KEY_EXTRACTION_METHOD.md).
Там же объясняется, *почему* это вообще работает (коротко: приложение
держит свой кэш Tuya-устройств, включая `local_key`, простым JSON в памяти
после того как открыта карточка устройства - на диск ключ в
расшифрованном виде не пишется).

Родственный проект
[`danfoss-ally-local`](https://github.com/ivnlab/danfoss-ally-local)
(интеграция для Home Assistant, для которой этот инструмент и добывает
credentials).

## Чего инструмент НЕ делает

- Не рутирует телефон и не обходит никакую защиту - нужен уже имеющийся
  root (см. требования).
- Не обращается к облаку Danfoss/Tuya. Всё происходит в оперативной
  памяти собственного телефона через локальное `adb`/`frida`-соединение.
- Не отправляет `local_key` никуда наружу. Вывод идёт только в терминал
  (и опционально в локальный файл через `--out`).

## Требования

- Рутованное Android-устройство (реальный телефон или эмулятор) с
  установленным и залогиненным приложением Danfoss Ally
  (`com.danfoss.ally`). **Root нужно включить явно** - на эмуляторе он
  практически никогда не включён по умолчанию, это отдельная настройка
  (см. ниже).
- `adb` на компьютере, устройство подключено и авторизовано.
- `frida-server`, запущенный на устройстве (версия должна совпадать с
  локальным pip-пакетом `frida` и архитектурой процессора устройства).
- `pip install frida` на компьютере.

Протестировано на: Windows 11 (сборка 10.0.26100),
[LDPlayer](https://www.ldplayer.net/) 14.0.18.0. Другие версии
Windows/эмуляторы/реальные телефоны могут сработать, но не проверялись -
см. дисклеймер выше.

### Включение root в LDPlayer

Root **выключен по умолчанию**, его нужно включить вручную - иначе
`adb shell su` не сработает, даже если сам эмулятор запущен нормально:

1. Открыть настройки самого эмулятора (значок шестерёнки в боковой панели
   инструментов окна эмулятора, не настройки Android внутри него).
2. На вкладке **Basic settings** найти **Root permission** (формулировка
   может немного отличаться в разных версиях LDPlayer) и включить.
3. Перезапустить эмулятор, чтобы изменение применилось.

Проверить можно через `python check_env.py` - он сам проверяет
`adb shell su -c id`.

Сначала запусти [`check_env.py`](check_env.py) - он проверяет всё
перечисленное выше в режиме "только чтение" (ничего не пишет на
устройство) и сообщает, чего именно не хватает, а если `frida-server` ещё
не запущен - даёт точную ссылку на скачивание и adb-команды для запуска:

```bash
python check_env.py
```

## Использование

Проще всего через управляемый CLI - он сам прогонит проверку окружения,
подскажет когда именно открывать приложение и автоматически повторит
попытку при известном обрыве подключения (перезапустив приложение через
adb, если оно упало):

```bash
python cli.py --ip 192.168.1.50
```

Сначала он сам, автоматически, без какого-либо участия, пытается
зацепиться за процесс приложения (до 20 попыток, с перезапуском
приложения если оно упало - см. раздел про нестабильность ниже). Только
когда соединение стабильно установлено - один раз просит нажать Enter,
предварительно открыв карточку **шлюза** в приложении (именно это
подгружает `local_key` в память). Флаг `--auto` пропускает эту паузу
(полезно только если точно знаешь, что карточка уже открыта - например,
для быстрого повторного прогона).

Результат: таблица всех найденных в памяти устройств (`devId`, `name`,
`nodeId`/cid, `parentDevId`), устройство с непустым `local_key` выделено
как шлюз, и готовый к вставке Python-сниппет (`GATEWAY_ID` /
`GATEWAY_HOST` / `GATEWAY_LOCAL_KEY` / `RT_DEVICES`) в формате
`credentials.py`, который использует интеграция
[`danfoss-ally-local`](https://github.com/ivnlab/danfoss-ally-local).
Добавь `--out credentials.py`, чтобы сразу записать сниппет в файл.

### Вручную, по шагам

Если хочется запускать два скрипта по отдельности (например, чтобы
пересканировать без повторной проверки окружения каждый раз):

1. Открой приложение Danfoss Ally, убедись что залогинен и список
   устройств загрузился с актуальными данными.
2. Открой карточку **шлюза** хотя бы один раз (тап по плитке - внутри
   ничего нажимать не нужно). Открывать карточки каждого RT для `nodeId`
   не обязательно (он приходит вместе со списком устройств), но и не
   помешает.
3. Запусти сканер напрямую:

   ```bash
   python get_local_key.py --ip 192.168.1.50
   ```

Если он упрётся в обрыв подключения (см. ниже), он просто завершится -
именно `cli.py` умеет повторять попытку сам.

## Если ничего не нашлось

- **Нет совпадений `localKey` с непустым значением**: скорее всего
  карточка шлюза не открывалась в текущей сессии приложения. Открой её,
  повтори запуск.
- **Процесс приложения не найден**: приложение должно быть на переднем
  плане (или хотя бы недавно открыто) - Android может выгрузить процесс
  в фоне, а вместе с ним и закэшированные данные из памяти.
- **attach падает / процесс приложения умирает**: см.
  [«Известная нестабильность»](#известная-нестабильность-attach-иногда-убивает-приложение)
  ниже - `cli.py` повторяет это автоматически, `get_local_key.py` напрямую -
  нет.
- **В таблице нет суб-устройств**: открой сам список устройств (не только
  карточку шлюза), чтобы `deviceTopo`/`nodeId` каждого RT успели
  подгрузиться.

## Известная нестабильность: attach иногда убивает приложение

На LDPlayer-окружении, где инструмент разрабатывался и тестировался, вызов
`attach()` из `frida` примерно в 1 случае из 3-4 убивает процесс целевого
приложения - стабильно воспроизводится. Проверено напрямую (сессия
разбора - см. историю коммитов/issue):

- Это не проблема ARM-на-x86 трансляции - подтверждено самим Frida
  (`realm='emulated'` даёт ошибку "process is not using emulation" в этом
  окружении), то есть дело не в инструментировании транслированного кода.
- Это не проблема недостаточной задержки после запуска - при повторном
  тесте с заметно большей паузой перед attach падения происходили с той
  же частотой.
- В `logcat` в момент падения нет вообще никакой сигнатуры краша - ни
  нативного fatal signal, ни tombstone, ни необработанного Java-исключения.
  Процесс просто молча исчезает из поля зрения ActivityManager примерно
  через 2 секунды после попытки attach - больше похоже на убийство извне,
  чем на настоящий краш, но точный триггер так и не установлен.

`cli.py` обходит это автоматическим тихим циклом повторов (до 20 попыток)
ещё *до* того, как попросит взаимодействовать с приложением - на практике
достаточно максимум одного повтора, чтобы получить стабильное соединение.
Если в вашей среде это происходит заметно чаще, чем "обычно получается за
1-2 попытки" - это ровно тот случай, о котором стоит написать issue.

## Файлы

- `cli.py` - управляемая точка входа: запускает оба скрипта ниже по
  очереди, с автоматическим повтором/перезапуском при обрыве подключения.
- `check_env.py` - проверка окружения/предпосылок в режиме только чтение.
- `get_local_key.py` - сканер памяти + генератор сниппета для
  `credentials.py`.
